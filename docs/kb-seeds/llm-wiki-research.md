# LLM Wiki 技术调研:让知识库自己长出来

> 探小虎 · 技术调研

每个团队的 Wiki 都逃不过同一个死循环:**没人写**(写文档的时间排不上优先级)→ **写了搜不到**(搜的人换五个关键词就放弃)→ **写了会过期**(产品改版了,文档还是三个月前的)。最后 Wiki 变成「巨大的文档墓地」,新人入职第一天满怀希望点进去,第三天就再也没打开过。

LLM 出现之后,这个死循环的三个环节——**知识的生产、检索、维护**——第一次都有机会被自动化。这篇调研把我最近看到的路线和自己的落地实践捋一遍:三条路线各自解决什么、坑在哪、怎么组合。

---

## 一、先定义问题:Wiki 到底差在哪

传统 Wiki 的失败,不是工具不好,是**三个环节全靠人工**,而人工的每个环节都在漏:

| 环节 | 靠人工时的死穴 |
|:---|:---|
| **生产** | 写文档没有绩效,排期永远让位给需求 |
| **检索** | 关键词搜索对黑话、同义词、换种问法无能为力 |
| **维护** | 没人负责过期检测,文档静默腐烂 |

LLM 对这三个环节各有一条改造路线。**先记住这个框架,后面所有调研对象都能装进去**。

---

## 二、路线一:LLM 生成 Wiki——解决「没人写」

代表:**DeepWiki**(Cognition,Devin 同门)及其开源平替 **DeepWiki-Open**。给一个 GitHub 仓库,自动产出一个结构化的 Wiki 站点:模块划分、逐文件讲解、页面间的引用链接、Mermaid 架构图。

它的生成管线基本是:

```
仓库 clone → 结构分析(目录树/依赖图)
          → 逐文件/模块摘要(LLM)
          → 规划 Wiki 目录(按「人想怎么读」重组,不是照抄目录树)
          → 分页生成 + 图 + 引用锚点
```

两个值得抄的设计:

1. **目录规划与文件结构解耦**。代码目录是「给机器看的」,Wiki 目录是「给新人看的」——按认知顺序重排(先总览、再核心流程、最后细节),这是 LLM 参与度最高、价值最大的一步。
2. **引用锚点**。每段生成的解说都锚到源文件/源码行,点引用能跳原文。这既是「溯源」,也是**控制幻觉的手段**:生成内容必须能指回证据。

> 一句话概括:路线一解决**冷启动**——把「没文档」变成「有 70 分的文档初稿」,把写文档的成本从「人工写作」降到「人工审校」。

**边界也要说清楚**:它生成的是「代码在做什么」,不是「为什么这么设计」和「业务背景」。设计决策类知识仍然要人来补。另外,仓库一变 Wiki 就烂——生成必须挂在事件上(合并、发版触发重生成),不然就是又一个墓地。

---

## 三、路线二:Wiki 作为检索源——解决「搜不到」

这是我在运维知识问答项目里落地的路线,也是我认为**投入产出比最高**的一条:不急着让 LLM 写 Wiki,先让现有的 Wiki 被检索得动。

核心方案是「**结构化 Wiki 检索 + 向量语义检索**」双混合,按 query 特征动态切换三种策略(纯结构 / 纯向量 / 混合):

```
              ┌─ 精确术语/黑话/产品名 → 结构化检索(标题路径/关键词)
用户 query ──→│
              └─ 自然语言/口语化问法 → 向量检索
                     ↓
        向量粗排 Top-20 → Cross-Encoder 重排 Top-3 → 拼 Prompt
```

为什么 Wiki 结构这么值钱?调研下来三个原因:

| Wiki 的结构特性 | 对检索的价值 |
|:---|:---|
| 标题层级 | 切片按标题切,天然语义完整;命中后还能**回调父级章节补上下文** |
| 命名规范 | 内部黑话、产品简称在向量空间里是弱点,在**精确匹配里是强项**——双路混合就是互相兜底 |
| 页面归属 | 检索结果天然带「属于哪个产品/模块」,权限过滤和来源标注都有了着落 |

配套的工程细节(展开见往期《RAG 实战》):Markdown 标题层级优先切片、表格/代码块不切断、黑话别名映射做 query 改写、**P0-P4 分级检索**(命中关键词才检索、非本领域问题导向官方文档并标来源、判断不了就反问)。

> 一句话概括:Wiki 的结构不是给人看才存在的,它是**检索质量的放大器**。同等内容,结构化 Wiki 检索比裸文档向量检索准得多。

## 四、路线三:LLM 维护 Wiki——解决「会过期」

前两条路线还只是「用 LLM 消费 Wiki」,更进一步的是让知识**沉淀回流**:

```
对话/工单/复盘记录 → LLM 抽取知识条目
                  → 判断挂到哪个 Wiki 节点(或新建)
                  → 与现有条目冲突检测
                  → 置信度分级:高置信自动挂载 / 低置信进人审队列
                  → Wiki 自愈更新
```

关键设计就一个:**抽取容易,挂载和冲突难**。调研下来的经验:

1. **不追求全自动**。知识条目按置信度分流,高置信(有明确来源、与现有内容不冲突)自动挂,其余进人审队列——对应我在检索里用的分级思想,这里同样适用。
2. **冲突检测比生成重要**。旧条目说「配额上限 100」,新工单说「已调整到 200」,不检测冲突就会同时存在两个「真相」。让 LLM 做条目间的一致性比对,输出「更新/合并/标记过期」三种动作。
3. **过期检测事件化**。产品发版、配置变更这类事件,自动标记受影响的 Wiki 页面进复核清单——把「文档腐烂」从静默变成显式待办。

> 这条路线本质是把公众号之前聊过的「Agent 长期记忆」从个人级放大到团队级:Wiki 就是团队的**外置记忆**,LLM 负责记忆的写入与整理,人负责记忆的裁可。

---

## 五、三条路线怎么组合:飞轮

三条路线不是三选一,是**一个闭环的三个阶段**:

```
        ┌────────────────────────────────────────┐
        │                                        │
   生成(冷启动)──→ 检索(消费提效)──→ 沉淀(回流维护)──┘
   路线一            路线二             路线三
   补齐存量          先见效            逐步自动化
```

| | 路线一:生成 | 路线二:检索 | 路线三:维护 |
|:---|:---|:---|:---|
| 解决 | 没人写 | 搜不到 | 会过期 |
| 成熟度 | 工具成熟(DeepWiki 类) | 方案成熟,工程量大 | 探索期,人审不可省 |
| 落地优先级 | 第二步(补存量) | **第一步(先见效)** | 第三步(积累数据后) |

**为什么检索先做?** 因为它不依赖 Wiki 质量达标就能见效,而且检索日志(用户搜什么、点没点、赞没踩)恰好是后两步最需要的训练素材——这就是飞轮转起来的第一步。

## 六、工具盘点与选型

| 工具 | 定位 | 适合 |
|:---|:---|:---|
| DeepWiki | 闭源 SaaS,仓库 → Wiki 效果标杆 | 开源项目/愿意上传代码的团队 |
| DeepWiki-Open | 开源平替,可私有化 | 代码不出域的企业 |
| Wiki.js/语雀 + LLM 插件 | 传统 Wiki 补 AI 检索 | 已有 Wiki 资产、只想加检索 |
| Dify 等知识库平台 | 低代码 RAG 问答 | 快速验证,深度定制受限 |
| 自研(检索管道 + 生成管线) | 全链路可控 | 有工程团队、知识是核心资产 |

选型建议只有一条:**先想清楚知识不出域是不是硬约束**,它直接决定 SaaS 还是私有化;然后从路线二起步,别一上来追求全自动。

---

## 七、写在最后

调研到最后,我的结论是:**LLM Wiki 的本质不是「AI 写文档」,而是把 Wiki 从「静态文档」升级成「活的团队记忆」**——生产靠生成、消费靠检索、新陈代谢靠沉淀回流,人只在关键节点做裁可。

死循环破掉的那一刻,不是某个工具上线,而是「写文档」第一次有了即时回报:你写的条目,明天就能被检索命中、被引用溯源。**知识管理最大的激励问题,LLM 用「看得见的复利」解决了。**
