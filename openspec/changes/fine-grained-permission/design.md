## Context

当前 JARVIS 系统基于 Spring Security + JWT 实现认证，但只有"是否登录"的粗粒度控制。所有登录用户拥有完全相同的权限。系统已有的模块包括：对话、知识库、分析仪表盘、推理调试、用户画像、任务管理等。详见 proposal.md。

## Goals / Non-Goals

**Goals:**
- 实现三级权限控制：菜单级、操作级（接口/按钮）、数据级（知识库内容）
- 基于 RBAC 模型，支持角色自定义和权限灵活配置
- 渐进式接入：不一次性锁死所有功能，按模块逐步加权限注解
- 向后兼容：已有用户和数据不受影响

**Non-Goals:**
- 不做细粒度字段级权限（行级/列级）
- 不做 ABAC（基于属性的访问控制），当前场景 RBAC 足够
- 不做组织架构/部门层级的权限继承
- 不做前端权限的实时推送，靠 token 刷新/重新加载实现

## Decisions

### 决策 1：采用 RBAC 而非 ABAC

**选择**：RBAC（用户 → 角色 → 权限）

**理由**：
- JARVIS 当前用户量小，角色数量有限（admin / user / 自定义少量角色），RBAC 完全够用
- 实现简单、概念清晰、易于理解和管理
- ABAC 虽然更灵活，但引入策略引擎复杂度高，维护成本大

**备选**：
- ABAC：灵活但过重，适合大型企业级系统
- 直接用户-权限关联：无角色层，配置繁琐，不可扩展

### 决策 2：权限编码三段式命名

**选择**：`<模块>:<资源>:<操作>`，如 `knowledge:document:delete`

**理由**：
- 层次清晰，阅读时一眼看出属于哪个模块的什么操作
- 支持通配符匹配：`knowledge:*` 表示知识库模块全部权限
- 与 Spring Security `hasPermission()` 注解天然契合

菜单权限用 `menu:<key>` 格式，与操作权限区分开。

### 决策 3：权限缓存放在 SecurityContext，用版本号触发刷新

**选择**：用户权限在登录时加载，存入自定义 `UserDetails`，通过 Redis 或数据库中的 `permission_version` 字段控制缓存失效。管理员修改角色权限时，递增受影响用户的版本号，下次请求校验版本不一致则重新加载。

**简化方案（当前采用）**：不引入 Redis，每次请求从数据库加载权限会有性能开销。折中方案：权限存入 JWT token（字符串列表），角色变更时要求用户重新登录生效。后续量大了再升级为缓存+版本号方案。

**理由**：
- 当前用户量小，重新登录的成本可接受
- JWT 自带权限信息，零数据库查询
- 实现最简单，不引入额外依赖

### 决策 4：数据权限通过 SQL 拼接 WHERE 条件实现

**选择**：知识库检索时，在 MyBatis Mapper 层动态拼接数据权限过滤条件。

**理由**：
- 在查询层过滤最可靠，不会因为上层遗漏而出问题
- 管理员直接跳过过滤，性能最优
- 实现简单，不需要额外的中间件或代理

**备选**：
- Hibernate Filter / AOP 拦截：更统一但侵入性强，当前项目用 MyBatis 不太适配
- 检索后内存过滤：数据量大时性能差

### 决策 5：渐进式接入 — 白名单模式

**选择**：默认放行（无权限注解的接口可访问），逐个接口加权限注解。

**理由**：
- 避免一次性改造所有接口导致大面积回归
- 可以按优先级逐步接入：先知识库，再对话，再管理功能
- 风险可控，随时可以回滚

### 决策 6：知识库访问范围三档

**选择**：public / private / role_based

**理由**：
- 覆盖绝大多数场景：全公开、个人私有、按角色共享
- 实现成本适中，三档逻辑清晰
- 不做"指定用户"级别——角色已经可以表达分组关系，不需要再加一层用户-文档直接关联

### 决策 7：Agent Skill 权限在 SkillResolver 层过滤

**选择**：在 `SkillResolver.resolve()` 解析出 skill 对应的工具白名单后，再根据用户权限二次过滤，只保留用户有权使用的工具。

**理由**：
- 离 Agent 创建最近，在源头就把无权限的工具排除，最安全
- 复用现有的 SkillResolver 解析流程，侵入性最小
- 权限编码 `agent:skill:<skill-name>:use` 与操作权限编码格式一致，便于管理

**备选**：
- 在 Tool 执行前 AOP 拦截：可以做更细粒度的控制，但性能开销大，且每个工具调用都查一次权限
- 在前端选择器过滤：体验好但不安全，后端仍需校验（作为辅助手段）

### 决策 8：工具级权限 — 创建时过滤 + 执行时二次校验

**选择**：两层防护——AgentFactory 创建 Toolkit 时过滤一次（创建时过滤），工具执行的统一入口（Toolkit.execute）再校验一次（执行时校验）。

**理由**：
- 防止 Prompt 注入绕过：Agent 可能被诱导调用不在白名单内的工具，执行时二次校验是最后一道防线
- 创建时过滤是性能优化——大部分调用在创建时就排除了，执行时校验是安全兜底
- 两层防护的实现成本都不高，但安全性显著提升

**备选**：
- 只做创建时过滤：简单但不够安全，Prompt 注入可能绕过
- 只做执行时校验：最安全但性能差，每个工具调用都要查权限

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 权限存在 JWT 中，角色变更后不能实时失效，需要重新登录 | 当前阶段可接受；后续可加版本号 + 拦截器重载机制 |
| 渐进式接入期间，部分接口无权限保护 | 按优先级排序，先保护敏感接口（删除、管理功能） |
| 数据权限 SQL 拼接容易遗漏 | 统一封装 `DataPermissionInterceptor` MyBatis 插件，自动注入过滤条件 |
| 前端按钮权限和后端接口权限可能不一致 | 统一权限编码，前端从后端拉取权限列表，不硬编码 |
| 角色删除后用户 token 中还有旧权限 | token 过期时间短（7天），最多 7 天失效；紧急情况可强制登出 |
| Agent 通过 Prompt 注入调用无权限工具 | 两层防护：创建 Toolkit 时过滤 + 工具执行入口二次校验 |
| Skill 权限和工具权限粒度不一致导致管理复杂 | 先做 Skill 级（粗粒度），工具级（细粒度）作为高级功能后续按需开放 |
| 权限校验增加 Agent 调用延迟 | 创建时过滤减少运行时开销；权限列表在内存中，查询是 O(1) 的 HashSet 操作 |

## Migration Plan

1. **V1 迁移**：执行 Flyway V11，创建角色/权限表和关联表，新增知识库访问范围字段，插入默认角色和权限
2. **数据迁移**：已有用户自动分配 user 角色，已有知识库文档默认为 public
3. **后端接入**：先加权限框架和工具类，现有接口全部放行
4. **前端接入**：菜单动态渲染 + 按钮权限指令，按菜单权限控制显示
5. **逐模块加权限注解**：从管理功能开始 → 知识库 → 对话 → 其他
6. **验证**：用 admin 和普通用户分别验证各模块权限

**回滚策略**：所有权限注解都是加条件判断，移除注解即可恢复放行。数据库迁移有 IF NOT EXISTS 保护，可重复执行。

## Open Questions

- 是否需要"部门/团队"级别的权限分组？当前 RBAC 角色模型不支持层级关系
- 权限变更通知是否需要更实时（如 WebSocket 推送），还是重新登录即可？
- 知识库文档的 role_based 权限是否需要支持"只读"和"可编辑"两种粒度？
